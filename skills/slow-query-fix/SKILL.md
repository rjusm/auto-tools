# Slow query → fix → MR

Вход: запрос из Grafana (панель MySQL process list): текст SQL, `Time`, `State`, `User/Host`, по возможности — сколько раз встречается.
Если Jira-ключа нет — спроси его (нужен для имени ветки и коммитов).

**Главное ограничение: в проде есть таблицы с миллионами строк.** Любое решение должно быть безопасно именно на таких объёмах — и для самого запроса, и для миграции. Всё, что проверено только на пустой локальной БД, считается непроверенным.

Никогда не выполняй ничего против прод/тест БД. Только локальный docker. Пароли и дампы с реальными данными в чат/репозиторий не выносить.

## 0. Telegram-уведомления и остановка

Общие правила и настройка — в [`tools/shared/TELEGRAM_GATE.md`](../../tools/shared/TELEGRAM_GATE.md), прочитай перед стартом. Для этого скилла дополнительно:
- Этапы для `notify`: старт и каждый из шагов 1–5.
- Обязательно `gate` (а не `notify`): перед шагом 3 (выбранное решение), перед наполнением данными (шаг 4.2, укажи объём), перед применением правки/миграции (4.4), перед созданием ветки/коммита/push (шаг 5).
- Типичное число шагов для `--step N/M`: 8–10 (старт, 1, 2, 3(gate), 4.1, 4.2(gate), 4.3, 4.4(gate), 4.5, 5(gate)).

## 1. Разобрать запрос
- Нормализуй: подставь плейсхолдеры (`?`, литералы → `:v`), выпиши таблицы, WHERE/JOIN/ORDER BY/LIMIT, функции над колонками.
- Сразу отметь подозрительное: `LIKE '%x'`, функции/касты над индексируемой колонкой (`DATE(created_at)`, `LOWER()`), `OR` по разным колонкам, `OFFSET` на больших значениях, `COUNT(*)`/`DISTINCT` без индекса, `SELECT *`, `ORDER BY` без подходящего индекса (filesort), неявное приведение типов (строка vs int/uuid), N+1 (много одинаковых коротких запросов).
- Если запрос — один из N одинаковых, долгий из-за блокировок (`State: Waiting for ... lock`, `Sending data` у UPDATE) — это другая проблема: ищи длинные транзакции, а не индекс.

## 2. Найти источник в коде
- Eloquent/Query Builder не оставляют SQL в коде как есть. Ищи по: имени таблицы (`Grep` по `'table_name'`, `->table(`, `$table =`), уникальным колонкам/значениям фильтров, raw-фрагментам (`whereRaw`, `selectRaw`, `DB::raw`).
- Проверь все слои: `app/Models`, `app/Services`, `app/Http/Controllers`, фильтры (`QueryFilter`/`DBFilter`, макрос `filterBy`), экспорты, консольные команды/джобы (`app/Console`, `app/Jobs`) — долгие запросы часто из отчётов, экспортов и кронов.
- Подтверди источник: воспроизведи SQL локально через `->toRawSql()` / `DB::listen` (в local он уже пишет SQL в лог с временем) и сверь с запросом из Grafana. Если не сходится — источник найден неверно, продолжай поиск.
- Покажи пользователю: файл:строка, кто это вызывает (роут/команда/джоб), как часто.

## 3. Выбрать решение (по возрастанию рискованности)
1. Переписать запрос: убрать функцию над колонкой (диапазон вместо `DATE()`), точное совпадение вместо `LIKE '%…%'` где допустимо, выбирать только нужные колонки, keyset-пагинация вместо `OFFSET`, `exists` вместо `count`, `chunkById`/`cursor` для обходов, кэш для тяжёлых агрегатов, вынос тяжёлого в очередь.
2. Добавить/изменить индекс (составной, порядок колонок: равенство → диапазон → сортировка; проверь, нет ли уже подходящего/дублирующего индекса: `SHOW INDEX`).
3. Изменить схему/архитектуру (партиционирование, агрегирующие таблицы) — только предложить пользователю, не делать самовольно.

Для каждого варианта явно оцени: что изменится по плану, не сломается ли бизнес-логика (результат должен остаться идентичным — сравни результаты до/после), влияние на запись (каждый индекс замедляет INSERT/UPDATE).

**Миграции на больших таблицах:**
- `ALTER TABLE ... ADD INDEX` на таблице с миллионами строк в проде — отдельный риск. Выясни у пользователя версию и движок прод-БД (MySQL/MariaDB, версия); локальный compose — `mariadb:10.3`, он может отличаться от прода.
- Явно указывай `ALGORITHM=INPLACE, LOCK=NONE` через `DB::statement`, чтобы ALTER упал, а не заблокировал таблицу, если режим недоступен. Не использовать `->change()` и смену типа колонки на больших таблицах без обсуждения.
- Нужен рабочий `down()`. Имя индекса задавать явно.
- В MR обязательно указать: размер таблицы (примерно), ожидаемое время/нагрузка, рекомендацию запускать вне пика.

## 4. Воспроизвести локально (docker)
Окружение: `_docker/docker-compose.yml` (сервис `db`, порт `${MYSQL_PORT:-3307}`, root/`${MYSQL_ROOT_PASSWORD:-123456}`, adminer на 8061). Подними только БД: `docker compose -f _docker/docker-compose.yml up -d db`. Не ломай существующий volume с данными пользователя — если там уже есть рабочая БД, создай отдельную схему (`CREATE DATABASE es_wallet_perf`) и направь на неё `DB_DATABASE`.

1. Схема: прогнать миграции (`php artisan migrate`) в отдельную схему, либо взять `SHOW CREATE TABLE` нужных таблиц.
2. **Наполнить данными, сравнимыми с продом.** Порядок количества строк — как в проде (спроси или оцени по Grafana/пользователю), не меньше ~1–5 млн для проблемной таблицы. Генерация — серверная, SQL-ом, не циклом в PHP:
   - рекурсивный CTE / `INSERT ... SELECT` из таблицы-удвоителя (`INSERT INTO t SELECT ... FROM t` повторять), `seq_1_to_N` (MariaDB `SEQUENCE` engine), `RAND()`/`UUID()`.
   - Распределение значений должно быть реалистичным (перекос: несколько «горячих» клиентов/статусов, большинство строк — старые), иначе селективность и планы будут не как в проде.
   - Типы и формат ключей — как в проде (в проекте используются UUID — генерируй их же).
   - После загрузки выполни `ANALYZE TABLE`, чтобы статистика была свежей.
3. Базовая линия **до** правки: выполни запрос с теми же параметрами, что в Grafana, замерь время (минимум 3 запуска, первый «холодный»), сохрани `EXPLAIN` (в MariaDB/MySQL 8.0.18+ — также `ANALYZE`/`EXPLAIN ANALYZE`). Убедись, что проблема **воспроизвелась** (запрос реально медленный и план похож на прод: full scan, filesort, temporary). Если не воспроизводится — данные нереалистичны, а не проблема «решена»; перегенерируй.
4. Примени правку (код и/или миграция через `php artisan migrate`), замерь **после** тем же способом. Сравни:
   - время, `type`/`key`/`rows`/`Extra` в EXPLAIN (`Using filesort`, `Using temporary`, `Using where` по полному скану);
   - **идентичность результата** (хеш/`COUNT`/`EXCEPT` по выборке до и после);
   - для миграции — время `ALTER` на полном объёме и что запись в таблицу не блокировалась.
5. Прогони затронутые тесты (`vendor/bin/phpunit --filter ...`), если они есть для этого кода.

Не заявляй «ускорилось», пока нет цифр до/после на объёме данных, сопоставимом с прод. Если выигрыша нет или он в пределах шума — так и скажи и вернись к шагу 3.

## 5. Подготовить MR
Только после подтверждённого результата. Ветку, коммит и push делай **только по подтверждению пользователя**.
- Ветка от `developer`: `fix/<JIRA-KEY>-<кратко>` или `EW-xxx-...` по принятому в репозитории (смотри `git log`). Изменения минимальные: только то, что относится к запросу. Не коммить `.env`, дампы, локальные скрипты генерации данных (если они полезны — предложи положить в `docs/` отдельно).
- Коммиты в стиле репозитория: `<KEY> perf: <что сделано>`.
- Описание MR — по `.github/PULL_REQUEST_TEMPLATE.md` (можно вызвать скилл `anthropic-skills:pr-desc`). В `[TASK DESCRIPTION]` обязательно:
  - исходный запрос и его время в Grafana;
  - откуда вызывается (файл:строка, роут/команда);
  - причина (план из EXPLAIN);
  - что изменено;
  - **таблица «до/после»**: объём данных, время, EXPLAIN (ключевые поля);
  - риски для больших таблиц (миграция: ожидаемое время, `ALGORITHM/LOCK`, рекомендация по окну выкатки);
  - как проверить на тесте.
  В `[MIGRATION]` — «да/нет» и какая.
- В конце: ссылка/ветка, краткий итог цифрами, что не проверено (например, расхождение версий БД локально и в проде).

## Формат отчёта пользователю по ходу работы
После шагов 1–2 коротко покажи: нормализованный запрос, найденный источник, гипотезу причины и план решения — и только потом переходи к воспроизведению. Если по запросу нельзя однозначно найти источник или решение требует смены схемы/архитектуры — остановись и спроси.
